## ch2 Rodrigo Recio (PT-BR)

### 1. TabNews — post
**Título:** `n_threads` no máximo derruba o clock
**Corpo:**
Subir `n_threads` até o número de núcleos lógicos parece de graça. No Ollama, o que acontece é o contrário: o processo ocupa os núcleos de eficiência, o clock cai, e o tok/s piora.

O teste curto é um único chat, mesmo modelo, mesmo prompt. Anota o clock da GPU/CPU e o tok/s com `n_threads` no máximo e de novo com um valor perto dos núcleos de performance. Se o clock caiu e o tok/s não subiu, o máximo era o problema.

O vídeo mostra a comparação: https://www.youtube.com/watch?v=f38-AL7yK4Q

### 2. r/brdev — post
**Título:** KV em FP16 estoura 8GB antes do modelo "caber"
**Corpo:**
O cartão da GPU diz 8GB e o GGUF do modelo cabe. O que não cabe é o KV cache em FP16 junto com o contexto que você pediu. O servidor recusa o load e parece que "o modelo não roda".

Antes de trocar de quantização, olha o tipo do KV. q8 no cache muda o que cabe; FP16 no mesmo contexto estoura. Vídeo com o caso: https://www.youtube.com/watch?v=aKBw0nv_CPs

### 2. dev.to — post
**Title:** Your plugin manifest ran a shell before the tool loaded
**Body:**
If an agent plugin shells out while it is still loading, the tool call you are debugging is not the first process. The manifest already ran.

Check the load path before you blame the model: what executes between "plugin enabled" and "tool registered"? On one of ours, that gap was a shell in the manifest. The short walks the order: https://www.youtube.com/watch?v=_M1y7vw7Qyo
